# BREAKAGE.md

Every real bug hit during the build, one line each: what broke, the root cause, the fix.

- 2026-08-25: guard tests exploded with SyntaxError on shop/app.py — a PowerShell `Set-Content -Encoding utf8` edit wrote a UTF-8 BOM that ast.parse rejects; stripped the BOM, guard tests now read files as utf-8-sig, and file edits go through the Write/Edit tools instead of Set-Content (known Round-1 gotcha family).
- 2026-08-25: /order answered malformed JSON bodies with a bare 500 — request.json() was unguarded; all body parsing now goes through a json_body helper returning a typed BAD_REQUEST.
- 2026-08-25: lab scripts emitted SyntaxWarning "\\. is an invalid escape sequence" on Python 3.14 — PowerShell example paths (.\.venv\...) inside ordinary docstrings; fixed by making those docstrings raw strings.
- 2026-08-25: COUPON_INELIGIBLE responses returned `"code": "FRESH150"` instead of the taxonomy code — `VelcrowError.payload()` spread extra fields after the `code` key, so a `code=` kwarg shadowed the taxonomy; fixed by spreading fields first (taxonomy keys win) and renaming the field to `coupon_code`.

- 2026-08-25: writing Checkout.jsx through a quoted bash heredoc died with "unexpected EOF while looking for matching `''" — this harness mangles apostrophes inside heredocs (`human's`, `shop's`), a known Round-1 gotcha; wrote that file with the Write tool instead.
- 2026-08-26: the storefront showed its "could not reach the shop API" error state in Chrome while curl succeeded — uvicorn binds IPv4 127.0.0.1 only and Chrome resolves `localhost` to IPv6 ::1 first, so every browser fetch failed; pinned the frontend API bases to 127.0.0.1 and added the 127.0.0.1 storefront origins to both CORS allowlists.
- 2026-08-26: taking a reservation stored it server-side but the confirmation never appeared — the product page jumped back to the first in-stock size; the success handler called load(), which refetched the product and re-selected the default variant, unmounting the panel holding the confirmation. Reserving does not change stock, so the refetch was dropped entirely.
- 2026-08-26: a variant-less out-of-stock product (FreshKart ghee) read "Pick another pack above" and "Pack is out of stock" when there were no packs to pick — the out-of-stock copy assumed every product has variants; it now branches on whether the product actually has any.
- 2026-08-26: the agent told a Loomcraft shopper their subtotal was "₹329.80" when the cart held ₹3,298.00 — tool results returned raw integer paise and the model converted to rupees in prose, slipping a decimal place (the Round-1 "LLM misstates amounts" failure, recurring). Fixed at the root: one formatter in common/money.py, every tool result now carries ready-made *_display strings, and the system prompt forbids the model doing any money arithmetic or conversion.
- 2026-08-26: on "add 2 kg lemons under 100 rupees" the model sometimes passed variant="1 kg" to a variant-less product, wasting a round (the shop refused, the error was fed back, and it retried correctly — the loop self-corrected, so the outcome was right). Tightened the prompt: pass `variant` only when search_catalog returned a "variants" list, and treat a weight or pack size in the shopper's words as a quantity.
- 2026-08-26: with :8003 stopped, the widget showed the raw browser error "VelcrowAI could not start up here: Failed to fetch", which says nothing about the cause; boot failures that look like an unreachable service now name the service URL and print the uvicorn command to start it.
- 2026-08-26: "add lemons" silently added 1 kg instead of asking how many — the prompt told the model what to do when the variant was unstated but said nothing about an unstated quantity, so it defaulted to 1. Added an explicit stated/missing rule for both quantity and variant. First attempt over-corrected and made it ask even when "2 kg" WAS stated (it broke the acceptance sentence), so the rule was restructured to make acting the default and asking the exception; verified across four phrasings plus the follow-up turn.
- 2026-08-26: "okayy add" (agreeing to the agent's own question) did not add, and then "did u add" — a QUESTION — added a second pack, leaving the cart at x2. Three causes, three fixes: (1) the ask-rule only counted a quantity as stated if the current message held a number, so a bare agreement looped back to asking; (2) the model was invited to act on "did you add it", so questions now explicitly report via view_cart and never mutate, backed by a code-level one-add-per-product-per-turn guard in runtime.py (spec 7.9 - policy in code, not prompt); (3) ROOT CAUSE - only user/assistant TEXT was carried between turns, so previous search results were lost and the model invented item_ids like "long-grain-basmati-rice". The agent service now keeps the real message list (tool calls and results included) server-side per cart, trimmed on whole-turn boundaries.
- 2026-08-26: asked "what veggies you have", the agent answered "there are currently no vegetables listed in the catalog" while tomatoes sat in the catalog tagged "vegetable" — search_catalog did literal substring matching, so the plural "vegetables" never matched the singular tag, and the model reported one empty search as an absence. Two fixes: search now also matches on a crude singular stem, and a zero-match result carries catalog_overview (the whole shelf) plus a note telling the model to answer from it rather than denying stock.
- 2026-08-26: the "how I did this" strip (spec 6.5) was reported expanding to empty bullets - tool name, args, result summary and the model's why all blank, though all four were correct in the chain log. NOT REPRODUCED in a fresh session: the strip rendered every field correctly across both shops, 1-step and multi-step turns, success and refusal. What the audit did find is that the renderer made an empty bullet *possible and silent*: it assembled one `innerHTML` string from `s.tool`/`s.args`/`s.result_summary`/`s.why` with no fallback, so any field the server failed to send produced a blank row rather than a complaint, and the strip is the one surface that must not fail quietly (it is the evidence the agent chose its own actions). Rebuilt so the failure cannot recur or hide: the three display strings are now built server-side in `tools.call_display` / the `tool` SSE event (the same "format once on the server" rule the money bug forced, above), the widget sets them with `textContent` and substitutes a visible placeholder for anything missing, the strip now also renders on the error path, and four tests assert every tool event carries a complete, non-blank, rupee-correct line. Two contributing conditions were also removed: the bundle was served `Cache-Control: no-cache` (a revalidation the browser may skip - now `no-store`) and carried no version marker, so a stale cached widget was indistinguishable from a broken one; the root element now stamps `data-vc-build` and logs it at boot.
- 2026-08-26: the chain log rendered `₹` as three mojibake characters. The bytes on disk were correct UTF-8 all along - the corruption was in the READ: a BOM-less UTF-8 file is decoded as cp1252 by the default Windows toolchain (PowerShell 5.1 `Get-Content`, `type`, Notepad), turning one character into three. Fixed at the write path as asked, but by removing the ambiguity rather than adding a BOM (a BOM would break `json.loads` on line 1 and re-run the Round-1 BOM disaster recorded above): the JSONL is now written `ensure_ascii=True`, so the file is pure ASCII escapes that every tool on every platform decodes identically, and `json.loads` restores the exact `₹` on the way back in. Hashes are unaffected because they are taken over `canonical_json`, which is unchanged - chains written before this still verify, and a test asserts that. The scan for the read-side bug also turned up a genuine write-side one: `shop/app.py` carried a real mojibake em-dash inside a user-visible `PRICE_CHANGED` message, so a UTF-8-through-cp1252 round trip had already been committed to source; fixed, with a test that fails if any `.py`/`.js`/`.jsx` file grows one again.

- 2026-09-03: (WhatsApp addendum) THE PUNISHMENT ROLLED ITSELF BACK. The OTP verifier counted wrong attempts and burned the code after three - and then raised the error INSIDE `with sqlite3.connect(...)`, whose context manager rolls the transaction back on exception. So the attempt count silently reset to zero on every wrong guess and the burn never happened: unlimited tries, and the right code still worked after "too many wrong attempts". Caught by the test that tries three wrong codes then the right one (it verified, when it should be dead). The verifier now decides inside the transaction, commits the write, and raises AFTER the `with` block. Rule extracted: never raise an exception you care about from inside a sqlite context manager whose writes you also care about.
