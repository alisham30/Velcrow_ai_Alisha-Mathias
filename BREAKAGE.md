# BREAKAGE.md

Every real bug hit during the build, one line each: what broke, the root cause, the fix.

- 2026-08-25: guard tests exploded with SyntaxError on shop/app.py — a PowerShell `Set-Content -Encoding utf8` edit wrote a UTF-8 BOM that ast.parse rejects; stripped the BOM, guard tests now read files as utf-8-sig, and file edits go through the Write/Edit tools instead of Set-Content (known Round-1 gotcha family).
- 2026-08-25: /order answered malformed JSON bodies with a bare 500 — request.json() was unguarded; all body parsing now goes through a json_body helper returning a typed BAD_REQUEST.
- 2026-08-25: lab scripts emitted SyntaxWarning "\\. is an invalid escape sequence" on Python 3.14 — PowerShell example paths (.\.venv\...) inside ordinary docstrings; fixed by making those docstrings raw strings.
- 2026-08-25: COUPON_INELIGIBLE responses returned `"code": "FRESH150"` instead of the taxonomy code — `VelcrowError.payload()` spread extra fields after the `code` key, so a `code=` kwarg shadowed the taxonomy; fixed by spreading fields first (taxonomy keys win) and renaming the field to `coupon_code`.

- 2026-08-25: writing Checkout.jsx through a quoted bash heredoc died with "unexpected EOF while looking for matching `''" — this harness mangles apostrophes inside heredocs (`human's`, `shop's`), a known Round-1 gotcha; wrote that file with the Write tool instead.
- 2026-08-26: the storefront showed its "could not reach the shop API" error state in Chrome while curl succeeded — uvicorn binds IPv4 127.0.0.1 only and Chrome resolves `localhost` to IPv6 ::1 first, so every browser fetch failed; pinned the frontend API bases to 127.0.0.1 and added the 127.0.0.1 storefront origins to both CORS allowlists.
- 2026-08-26: taking a reservation stored it server-side but the confirmation never appeared — the product page jumped back to the first in-stock size; the success handler called load(), which refetched the product and re-selected the default variant, unmounting the panel holding the confirmation. Reserving does not change stock, so the refetch was dropped entirely.
- 2026-08-26: a variant-less out-of-stock product (FreshKart ghee) read "Pick another pack above" and "Pack is out of stock" when there were no packs to pick — the out-of-stock copy assumed every product has variants; it now branches on whether the product actually has any.
- 2026-08-26: the agent told a Loomcraft shopper their subtotal was "₹329.80" when the cart held ₹3,298.00 — tool results returned raw integer paise and the model converted to rupees in prose, slipping a decimal place (the Round-1 "LLM misstates amounts" failure, recurring). Fixed at the root: one formatter in common/money.py, every tool result now carries ready-made *_display strings, and the system prompt forbids the model doing any money arithmetic or conversion.
- 2026-08-26: on "add 2 kg lemons under 100 rupees" the model sometimes passed variant="1 kg" to a variant-less product, wasting a round (the shop refused, the error was fed back, and it retried correctly — the loop self-corrected, so the outcome was right). Tightened the prompt: pass `variant` only when search_catalog returned a "variants" list, and treat a weight or pack size in the shopper's words as a quantity.
- 2026-08-26: with :8003 stopped, the widget showed the raw browser error "VelcrowAI could not start up here: Failed to fetch", which says nothing about the cause; boot failures that look like an unreachable service now name the service URL and print the uvicorn command to start it.
- 2026-08-26: "add lemons" silently added 1 kg instead of asking how many — the prompt told the model what to do when the variant was unstated but said nothing about an unstated quantity, so it defaulted to 1. Added an explicit stated/missing rule for both quantity and variant. First attempt over-corrected and made it ask even when "2 kg" WAS stated (it broke the acceptance sentence), so the rule was restructured to make acting the default and asking the exception; verified across four phrasings plus the follow-up turn.
- 2026-08-26: "okayy add" (agreeing to the agent's own question) did not add, and then "did u add" — a QUESTION — added a second pack, leaving the cart at x2. Three causes, three fixes: (1) the ask-rule only counted a quantity as stated if the current message held a number, so a bare agreement looped back to asking; (2) the model was invited to act on "did you add it", so questions now explicitly report via view_cart and never mutate, backed by a code-level one-add-per-product-per-turn guard in runtime.py (spec 7.9 - policy in code, not prompt); (3) ROOT CAUSE - only user/assistant TEXT was carried between turns, so previous search results were lost and the model invented item_ids like "long-grain-basmati-rice". The agent service now keeps the real message list (tool calls and results included) server-side per cart, trimmed on whole-turn boundaries.
- 2026-08-26: asked "what veggies you have", the agent answered "there are currently no vegetables listed in the catalog" while tomatoes sat in the catalog tagged "vegetable" — search_catalog did literal substring matching, so the plural "vegetables" never matched the singular tag, and the model reported one empty search as an absence. Two fixes: search now also matches on a crude singular stem, and a zero-match result carries catalog_overview (the whole shelf) plus a note telling the model to answer from it rather than denying stock.
- 2026-08-26: the "how I did this" strip (spec 6.5) was reported expanding to empty bullets - tool name, args, result summary and the model's why all blank, though all four were correct in the chain log. NOT REPRODUCED in a fresh session: the strip rendered every field correctly across both shops, 1-step and multi-step turns, success and refusal. What the audit did find is that the renderer made an empty bullet *possible and silent*: it assembled one `innerHTML` string from `s.tool`/`s.args`/`s.result_summary`/`s.why` with no fallback, so any field the server failed to send produced a blank row rather than a complaint, and the strip is the one surface that must not fail quietly (it is the evidence the agent chose its own actions). Rebuilt so the failure cannot recur or hide: the three display strings are now built server-side in `tools.call_display` / the `tool` SSE event (the same "format once on the server" rule the money bug forced, above), the widget sets them with `textContent` and substitutes a visible placeholder for anything missing, the strip now also renders on the error path, and four tests assert every tool event carries a complete, non-blank, rupee-correct line. Two contributing conditions were also removed: the bundle was served `Cache-Control: no-cache` (a revalidation the browser may skip - now `no-store`) and carried no version marker, so a stale cached widget was indistinguishable from a broken one; the root element now stamps `data-vc-build` and logs it at boot.
- 2026-08-26: the chain log rendered `₹` as three mojibake characters. The bytes on disk were correct UTF-8 all along - the corruption was in the READ: a BOM-less UTF-8 file is decoded as cp1252 by the default Windows toolchain (PowerShell 5.1 `Get-Content`, `type`, Notepad), turning one character into three. Fixed at the write path as asked, but by removing the ambiguity rather than adding a BOM (a BOM would break `json.loads` on line 1 and re-run the Round-1 BOM disaster recorded above): the JSONL is now written `ensure_ascii=True`, so the file is pure ASCII escapes that every tool on every platform decodes identically, and `json.loads` restores the exact `₹` on the way back in. Hashes are unaffected because they are taken over `canonical_json`, which is unchanged - chains written before this still verify, and a test asserts that. The scan for the read-side bug also turned up a genuine write-side one: `shop/app.py` carried a real mojibake em-dash inside a user-visible `PRICE_CHANGED` message, so a UTF-8-through-cp1252 round trip had already been committed to source; fixed, with a test that fails if any `.py`/`.js`/`.jsx` file grows one again.
- 2026-08-26: (found while fixing the above, not reported) `runtime.run_turn` lost the conversation after any turn containing an add - the local `key` holding the conversation id `(shop_id, cart_id)` was reassigned inside the tool loop to the duplicate-add guard's `(item_id, variant)`, so the final `CONVERSATIONS[key] = ...` filed the whole thread under a product id. The next turn found nothing and fell back to text-only history: precisely the root cause recorded above as fixed, silently reintroduced by a name collision. Renamed to `convo_key` / `add_key`. This is load-bearing for Phase 5, where "my usual order" and "pay" both depend on the thread surviving the turn that built the cart.
- 2026-08-26: "what did I order last time?" answered "you have no orders" after a full restart, which looked exactly like state being lost from memory. It was not, and the reported diagnosis was wrong in an instructive way: purchase history was never in memory to begin with. Proven before changing anything - orders were on disk with their keys, `/orders/last` returned the right basket against a cold-started shop, `reorder_last` reads that endpoint (SQLite) and never touches `CONVERSATIONS`, and replaying the exact question through a cold `:8003` produced the correct history. TWO real defects, neither about persistence. (1) WRITE PATH: `web-shop/src/api.js` `order()` posted only `{cart_id}` - the storefront checkout, the main way anyone buys, never sent a shopper key at all, so 7 of 11 paid orders were written anonymous and were unfindable forever, restart or no restart. Only widget purchases carried a key. (2) IDENTITY SPLIT: the widget's storage-key fallback was `"velcrow-shopper-" + SHOP` ("grocery") while the server and storefront used `shop_id` ("freshkart"), so whenever `/agent/config` had not supplied the name the widget minted a SECOND identity under a different key - both were observed in one browser - and the shopper silently became a different person. Fixed: the key is now one shared module (`web-shop/src/shopperKey.js`) with names derived from `shop_id` on both sides and the fallback matching, and it rides on every order. Beyond the fix, added the portable half we discussed: a contact (phone/email) normalised in `common/contact.py` so "+91 98211 58848", "098211 58848" and "9821158848" are one shopper, a `shopper_links` table mapping the many browsers one person uses to one contact, retroactive claiming of orders bought before a contact was given, and an `identify_shopper` tool so the agent recovers the cross-device case in conversation. `tests/test_shopper_key.py` tears down every in-memory structure between write and read. Deliberately NOT persistent: the conversation thread (`runtime.CONVERSATIONS`) is in-process and dies with the service - a chat cannot resume after a restart, which is fine, but it is now provably not what loses an order. The contact is a claim and not a credential: it unlocks history only, and money still needs a mandate, a cart-bound approval and the wallet's five checks.
- 2026-08-26: THREE reported by the user in one go, two of them mine to own. (1) THE REVENUE LAB WAS FABRICATED. It ran 20 scripted goals through a simulation and multiplied them by follow-through rates I invented (0.35 of repeat shoppers reorder, 0.55 of reserved stock-outs come back), then printed the result beside real rupee figures as though both were measured. The user had made no unassisted sales at all, so a column reading "17 orders, Rs 27,210 without VelcrowAI" was pure invention. Rewritten to measure only paid orders in the two shops' own databases, with the assisted flag that is written at order time; where a counterfactual is unavoidable it is taken from the same real order by adding its own discount back. It now says when a side has no orders and when the sample is too small to generalise, instead of filling the gap. A scoreboard whose comparison column is a guess is worse than no scoreboard. (2) The part-fill popup said "held 9" when the shopper asked for 9 with 6 already in the basket - committing them to 15 of something they asked 9 for. Root cause was an ambiguity nobody had resolved: "9" means nine MORE to the agent and nine IN TOTAL on a product page whose stepper shows what you want to end up with. The shop was guessing. `fulfil` now takes an explicit `mode` of add or target, the storefront sends target, the agent sends add, and the button reads "Update basket to 9" when a line is already there. Held is now 3, and already + added + held equals what was asked for. (3) There was no sign-in anywhere. The shopper key and contact key had worked and been tested since Phase 7, but nothing in the UI ever surfaced them, so being remembered across a refresh was invisible and might as well not have existed. Added a header sign-in: a phone or email, no password (spec 14 bans accounts), restored on every load, showing the last order at today's prices, with a way to be forgotten.
- 2026-08-26: (Phase 8, a scope note rather than a bug) the Revenue Lab's first honest run showed AOV going DOWN with the agent (₹1,600.61 -> ₹1,456.08) and ₹2,076.80 of margin handed back in coupons. That is correct, not a defect: claiming coupons costs the merchant money, and the near-miss raises basket SIZE while giving the discount away. The lift is ₹1,911.34, of which ₹1,910.15 is rescued stock-outs - revenue that would otherwise have been zero. Recorded here because the temptation is to report only the lift; the scoreboard now shows the cost beside it, and a test asserts the discount and coupon counts are present. The pitch is "the agent recovers sales you were refusing", not "the agent makes coupons profitable".
- 2026-08-26: asking for more than the shelf held threw the excess demand away. "Add 16 wool scarves" with 12 in stock got a flat OUT_OF_STOCK at the cart, the agent came back with "shall I add 12 instead?", and the other 4 were lost - not sold, not reserved, not even recorded. Spec 7.2 makes a refusal into a reservation, and a partial refusal is still a refusal. Three separate defects. (1) `/reserve` refused outright while `stock > 0`, so a shortfall could not be held at all; the guard is now "you may reserve only what the shop cannot supply" (`stock >= qty`). (2) There was no single place that did the split, so the storefront and the agent would have drifted; added `POST /cart/{id}/fulfil`, which takes what the shelf allows, reserves the rest where the shop supports it, and always values the shortfall into the demand ledger - even at FreshKart, which takes no reservations but whose merchant should still see what they could not sell. (3) THE STUBBORN ONE: the model kept capping the request itself. Told "add 12", it read `stock: 5` out of the search result and called `add_to_cart(qty=5)`, so the shop never learned 12 were wanted and there was nothing to reserve. Two prompt rules failed to stop it. Fixed structurally instead, per this file's own repeated lesson: the model is no longer shown a stock NUMBER at all, only "in stock" / "only a few left" / "out of stock". It cannot cap to a figure it does not have, and the exact arithmetic belongs to the shop anyway. Also: `fulfil` initially ignored what was already in the basket, so adding 1 then 12 more left 13 in a cart backed by 12 units - caught by a test, fixed by counting the existing line against the shelf. `update_qty` now splits the same way, so "make that 10" cannot dead-end either. The storefront shows a dialog naming what went in, what is held, and what it is worth; the agent says the same thing in one sentence from a shop-supplied string.
- 2026-08-26: (Phase 7, found live) THE CHEAT-MERCHANT DEMO DID NOT WORK. With cheat mode on, Loomcraft quoted ₹961.82 for a ₹799.00 tee, the buyer agent paid it, and the shop's trust score went UP. The villain demo is one of two required failure demos (spec 12 phase 8, 15.6) and it would have failed on camera. Root cause was in the cheat itself, not the wallet: I had implemented it as an inflated QUOTE at `/order`, so the shopper was shown the inflated number, approved that number, and the approval was signed over it - every wallet check then agreed, correctly, because there was no disagreement to find. Spec 5.1 says the check catches a merchant altering the total "between approval and charge", which means the villain must quote HONESTLY and lie afterwards. Moved the inflation to `GET /order/{txn_ref}` - the charge the wallet actually fetches at check 4 - leaving line items true so the cart hash still matches and the lie has to be caught on the amount. Now: human approves ₹899.00, shop demands more, wallet raises PRICE_CHANGED, the buyer shows a red Blocked card, nothing is charged, and trust drops 0.8 -> 0.4. The Phase 6 test that had asserted the old behaviour was asserting the bug, so it was rewritten; a new test drives the full approve-then-refuse path.
- 2026-08-26: (Phase 7) the buyer ranked Crew Socks first for "cotton kurti" - socks matched on "cotton", and since price is the heaviest weight (0.4) and socks are cheap, they outranked the actual kurti. Arithmetically correct and obviously useless. `_matches` counted any term hit as a match; now a product must match every term in the query, with partial matches kept only as a fallback so a near miss still beats an empty page.
- 2026-08-26: (Phase 7) the buyer-agent tests were reaching the real network - the fixture patched `agent.buyer.httpx` but `agent/app.py` calls `httpx.post/patch` at module level to build the basket and place the order, so `/choose` talked to whatever happened to be listening on 8001/8002 and picked up cheat mode left on from a manual run. Fixed by routing both call sites in the fixture, with an explicit assertion that fails if a test tries to reach anything but an in-process shop.
- 2026-08-26: (Phase 6, found in the live comeback run) a restock marked every waiting reservation `notified` whenever the callback returned 2xx - but :8003 answers 200 with `{"offered": false}` when it declines to act (mandate revoked, or the reservation has no shopper reference to reach). So a shopper nobody could contact was recorded as contacted, and the reservation vanished from the merchant's open queue having rescued nothing. Delivered is not reached: the shop now closes a reservation only when an offer was actually made, and the chain entry says which of the three happened.
- 2026-08-26: paying left the basket full - the goods stayed in the drawer after a confirmed payment, so the badge kept its count and the next add stacked on top of items already bought. `/confirm-payment` marked the order paid and never touched the cart that produced it; nothing in the build ever emptied a cart. Basic commerce, missed while polishing conversation quality. Fixed at the shop (`db.clear_cart`, called from `/confirm-payment` only): an order that is merely created or that expires leaves the basket alone, because a shopper whose payment never completed still owns their basket. The emptied cart and its line count are named in the shop chain entry.
- 2026-08-26: the agent only ever mentioned coupons when asked, which makes the whole of spec 7.1 dead weight - the coupon-rescue pitch is "claiming coupons the shopper would forget", and a shopper who remembers to ask has not forgotten. In the Phase 5 acceptance run, "add 2 kg tomatoes" ended at "subtotal ₹371.00" with a ₹28 top-up to unlock FRESH50 sitting unmentioned; it surfaced only on an explicit "what coupons can I get". Root cause was structural, not a missing prompt line: `apply_best_coupons` was a tool the model had to *choose*, so noticing was optional. Fixed by removing the choice - every cart result (`add_to_cart`, `update_qty`, `remove_line`, `view_cart`) now carries a `savings` block with the claimed set and any near-miss as a ready-made sentence, so the model cannot move the cart without the answer arriving in the same tool result. Policy in code, not prompt, as with the quantity and cap checks. The trace strip shows it too (`cart 5 item(s), ₹371.00, near-miss FRESH50`), which is what makes the noticing visible rather than merely true. Prompt governs only the wording and the say-it-once rule; a dead coupon endpoint returns `{}` and can never break an add.
- 2026-08-26: (Phase 5 acceptance run) asked "what would my usual order cost today?" with lemons repriced overnight, the agent quoted the correct new total (₹423.00) but never said the price had gone UP - it listed today's figures as if they had always been so. The tool was returning `delta_display` per line, but as one field among a dozen in a list the model summarised past it. A shopper agreeing to "the usual" is agreeing to a price, so an undisclosed rise is a bait-and-switch, and spec 12's acceptance is explicitly "re-quotes with deltas". Fixed by making the movement impossible to miss rather than hoping the model notices: `reorder_last` now lifts changed lines into a ready-made `price_changes` sentence list, sets `any_price_changed`, and attaches an imperative note; the prompt rule is now a MUST with the reason attached. Re-verified live: "Lemons (1 kg) - ₹54.00 each (was ₹44.00 each, now up ₹10.00) ... up ₹20.00 from your last order." Same treatment for lines that have gone out of stock, so a reorder can never silently drop one.
- 2026-08-26: while validating the new conversation suite, reverting the catalog-vocabulary fix left `shoppers-word-is-not-the-shops-word` PASSING — the model simply searched a different word and routed around the broken matcher, so the case passed for the wrong reason. Not a product bug but a real gap in the suite's guarantees: conversation cases guard user-visible outcomes, and the deterministic unit tests (which did fail instantly) guard the mechanism. Recorded as a scope note in lab/conversations.json so the suite is not mistaken for mechanism coverage.
